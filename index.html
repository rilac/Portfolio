Project 1. 엔테나 — 문제 해결외부 API 한도 · LLM 비용 · 데이터 신뢰성
① 백필이 영원히 끝나지 않던 문제
공공데이터포털은 하루 호출 한도가 1만 건인데, 6년치(2020-01-02~) 일봉을 전부 받아야 했습니다. 종목별로 호출하면 하루 약 2,800콜이 나가 3년치도 못 받는 계산이라, 날짜(basDt) 단위로 그날 전 종목을 한 번에 받는 방식으로 바꿨습니다.
문제는 그다음이었습니다. 포털 응답이 일관되지 않았습니다. 데이터가 없는 날은 items를 빈 문자열로, 결과가 1건이면 배열 대신 객체로, 키가 틀리면 HTTP 200에 XML 에러를 실어 보내는 식이었습니다. DTO로 바로 바인딩하면 이런 경우마다 죽었기 때문에 JsonNode 트리로 파싱하도록 바꾸고, 수집할 게 없는 날과 아직 못 받은 날을 구분했습니다. 공휴일은 응답이 0건이라 계속 미수집으로 남아 매 회차 다시 호출되고 있었는데, 0건 응답도 수집 완료로 기록하게 고쳤습니다. 일봉 적재는 PostgreSQL의 ON CONFLICT upsert를 써서 같은 날을 몇 번 돌려도 결과가 같게 만들었습니다.
공휴일이 연간 약 50일인데 매 회차 재호출하면 시간당 600콜, 17시간이면 하루 한도를 다 쓰는 구조였습니다. 재호출이 0건으로 줄면서 이 문제가 풀렸습니다.
② LLM 키 토큰 고갈 — AI 호출 구조 전면 개편
전 종목을 미리 브리핑해 두는 방식은 팀 공용 LLM 키를 하루 만에 말려서 서비스 전체가 멈췄습니다. 개편 전에 실측해 보니 하루 약 1,600콜에 토큰 1.2M이 나가고 있었고, 내역은 뉴스 요약 약 900, 종목 브리핑 301, 투자 포인트 300이었습니다.
그래서 사용자가 실제로 열어본 종목만 그 시점에 생성하도록 바꿨습니다. 투자 포인트를 요청 시점 생성으로 전환하고, 같은 종목에 동시 요청이 몰려도 종목별 JVM 락으로 한 번만 호출합니다. AiClient에는 401이면 즉시 중단, 429면 백오프 재시도를 넣었고 OpenAI 호환 제공자로 교체할 수 있게(AI_BASE_URL) 열어뒀습니다. 출력은 temperature 0과, 입력에 없는 숫자를 차단하는 충실성 가드로 묶었습니다.
백엔드 테스트 574건이 전부 통과한 상태에서, 이제 하루 호출 수는 시장 브리핑 1건에 실제로 연 종목 수와 시즌 종료 수를 더한 값이 됐습니다.
③ 원장을 아무도 못 고치게 — append-only 트리거
온체인 앵커가 외부 증명이라면 DB에도 내부 증명이 필요했습니다. 권한 REVOKE는 테이블 소유자에게 걸리지 않고, ddl-auto가 돌려면 앱 계정이 소유자여야 해서 쓸 수 없었습니다.
대신 PostgreSQL BEFORE 트리거로 token_ledger·season_trades의 UPDATE/DELETE를 전부 거부했습니다. predictions는 판정 컬럼만 바뀌도록 허용해서 대상·방향·목표가·기간·등록시각은 불변이고, 리빌 전 salt는 @JsonIgnore로 직렬화를 막았습니다. 운영자나 관리자, 애플리케이션 버그까지 포함해 원장과 체결 기록을 고칠 수 있는 경로가 사라졌습니다.
④ 로컬에선 재현되지 않던 신규 가입 100% 실패
2026-09-03에 신규 구글 가입이 전부 500으로 실패했습니다. users.nickname을 NULL 허용으로 바꿨는데 ddl-auto: update는 기존 NOT NULL을 풀어 주지 않아서, 그보다 먼저 만들어진 배포 DB에만 옛 제약이 남아 있었습니다. 기존 회원 로그인은 INSERT를 타지 않아 멀쩡했고 로컬은 테이블을 새로 만들기 때문에 재현 자체가 되지 않았습니다.
매 부팅마다 도는 멱등 스크립트에 ALTER ... DROP NOT NULL을 추가했습니다(이미 NULL 허용이면 no-op). 이 파일을 ddl-auto가 못 고치는 옛 스키마를 모아 두는 자리로 정하고, Testcontainers로 NOT NULL을 다시 건 DB를 띄워 부팅 SQL이 실제로 푸는지 검증하는 테스트를 붙였습니다. 이제 배포 DB는 부팅할 때 스스로 복구되고, 같은 유형의 스키마 드리프트도 한 곳에서 처리합니다.

① 로그아웃했는데 계속 온라인이던 계정

① 세션에서 JWT로 넘어간 대가: 즉시 무효화가 안 된다
SPA로 프론트를 분리하면서 JWT를 도입했는데, 토큰이 탈취되면 만료 시점까지는 강제 로그아웃을 시킬 방법이 없었습니다.
그래서 원본 JWT는 Redis에 auth:access:<sha256> / auth:refresh:<sha256> 형태로 저장하고, 클라이언트에는 64자 해시값만 내려주는 Phantom Token 구조로 바꿨습니다(access는 응답 바디, refresh는 Path=/api/v1/auth인 HttpOnly 쿠키로). 요청이 오면 [0-9a-f]{64} 정규식으로 형식부터 걸러낸 뒤 Redis에서 원본을 조회하고, 서명·만료·typ을 검증합니다. typ 검증이 없으면 refresh 토큰을 access로 쓰는 교차 사용이 가능해집니다. Redis 키의 TTL을 토큰 만료 시간과 맞춰뒀기 때문에 만료를 따로 관리하는 코드가 필요 없고, 키 하나를 지우면 그게 곧 강제 로그아웃입니다. Redis를 무영속(--save '' --appendonly no)으로 둔 것도 같은 맥락으로, 재시작되면 전원 로그아웃되는 걸 보안 동작으로 삼았습니다.

운영 장애 — "타인 글 첫 조회에서만 500"
'16기 글만 안 보인다'는 제보로 시작됐습니다. 기수 필터 문제로 착각하기 딱 좋은 증상이었습니다. 실제 원인은 직전 릴리스에서 insertIgnore 6곳에 한꺼번에 붙인 @Modifying(clearAutomatically=true)였습니다. INSERT 직후 영속성 컨텍스트를 비우다 보니 이미 로드해둔 Post가 detach되고, author의 LAZY 프록시를 초기화하는 시점에 LazyInitializationException이 터졌습니다.
증상이 이상하게 부분적이었던 이유도 따로 있었습니다. 본인 글이나 24시간 내 재조회, touch 갱신은 애초에 INSERT를 타지 않아서 멀쩡했고, 실패하는 건 오직 첫 조회자뿐이었습니다. 신규 글은 모두가 첫 조회자다 보니 마치 전원이 실패하는 것처럼 보였을 뿐입니다. 같은 원인으로 신고 누적 자동 숨김 기능도 detach된 엔티티에 걸려 조용히 유실되고 있었는데, 이건 로그에 흔적조차 남지 않아서 한동안 몰랐습니다.
호출부에 이미 사전 존재 확인 가드가 있어서 clear로 얻는 이득이 없다는 걸 확인하고 6곳 모두에서 제거했습니다. 같은 실수가 반복되지 않도록 각 insertIgnore에 '켜지 말 것' 주석을 남기고, GlobalExceptionHandler가 500/503에 스택트레이스를 남기도록 고쳤습니다. 검증은 Mockito 대신 H2를 MySQL 모드로 띄워 실제 세션에 가까운 조건에서 회귀 테스트를 돌렸습니다.
catch로 막을 수 없던 중복 INSERT 500
좋아요를 더블클릭하거나 두 탭에서 동시에 조회하면 500이 났습니다. IDENTITY 전략이라 save()가 즉시 INSERT를 날리고, 유니크 위반이 나면 Hibernate가 트랜잭션을 rollback-only로 마킹합니다. 예외를 catch로 삼켜도 커밋 시점에 UnexpectedRollbackException이 터집니다.
그래서 6개 경로를 네이티브 INSERT IGNORE로 바꿔, 중복이 예외 대신 0행 반환이 되게 했습니다. 다만 FK나 NOT NULL 위반까지 경고로 강등되는 위험이 있어 사전 존재 확인 가드를 남기고, '가드를 제거하면 무증상 데이터 유실'이라는 경고 주석을 붙였습니다.
토큰 회전 · 운영 품질
RFC 9700 유예 창을 적용했습니다. 회전은 구 RT 삭제, tombstone, 신 RT 등록, 유예 마커까지 Lua 스크립트 하나로 원자 실행합니다. 유예(20s) 안의 재제시는 다중 탭 경합으로 보고 직전 RT를 다시 발급하고, 창 밖에서 온 것만 탈취로 판정해 전 세션을 폐기합니다.
Flyway는 V1부터 V17까지 관리하고, prod에서는 flyway.enabled와 ddl-auto: validate로 이중 검증합니다. V12에서 refresh_tokens 테이블을 폐기하면서 정리 스케줄러 31줄이 통째로 사라졌습니다(Redis TTL로 자연 만료).
아직 남은 부채도 알고 있습니다. 레이트리밋은 ConcurrentHashMap 인메모리라 단일 인스턴스를 전제로 합니다. Redis를 이미 쓰는데도 남겨둔 지점이라, 수평 확장할 때 INCR + EXPIRE로 교체해야 한다고 주석에 적어 두었습니다.

ProfileOverview엔테나MoToK안심식탁SOOP회고
회고 ① 못한 것과 한계아쉬운 지점을 알고 있다는 것이 다음 설계의 출발점입니다
하려고 했는데 못한 것
게임 세션 복구(MoToK)에서 끊긴 참가자가 GAME_START를 못 받는 문제를 0~3층으로 분해해 명세 개정 초안을 썼지만 팀 합의 전에는 서버 구현에 들어가지 않기로 해 0층(끊김 노출·강제 재접속·발행 실패 안내)까지만 구현했습니다. 1층 구독자 기반 roster 확정, 2층 세션 스냅샷 복구, 3층 ack로 반열림 소켓 탐지가 남았습니다.
미사용 코드 정리(MoToK)로는 BE 매핑 62개와 FE 호출 경로를 대조하고 Spring 빈 · enum JSON 값 · 동적 문자열 참조 3가지 오탐을 손으로 걸러 조사 문서까지 냈지만, 공용 코드라 팀 합의를 기다리며 한 줄도 지우지 않았습니다.
MoToK와 엔테나에서는 부하 테스트를 하지 못했습니다. 동시성 로직(SETNX 가드 · Lua 회전)을 Mockito 단위 테스트까지만 검증했고 k6·JMeter 같은 부하 스크립트는 끝내 쓰지 못했습니다. 팀이 관측 지표(actuator · node-exporter)를 붙여 둔 상태에서도 몇 명까지 버티는가에 숫자로 답하지 못했습니다.
SOOP은 모더레이션 강화와 북마크 폴더를 WORKLOG §6 백로그에 적어 둔 채로 마무리했습니다. 혼자 만드는 서비스라 무엇을 안 할지 정하는 일이 매번 가장 어려운 판단이었습니다.
팀이 넣어 둔 관리자용 Spring Batch 일별 통계가 실제 운영 판단에 쓰이지 않는다는 걸 확인하고, 안심식탁에서 폐기와 대체(활동 로그)를 내가 주도했습니다. 남겨두면 유지비만 드는 코드였습니다.
전체 테스트가 OutOfMemoryError로 깨지던 문제를 힙을 늘리는 대신 컨텍스트 캐시를 32개에서 8개로 줄이고 ddl-auto: create를 쓰는 방식으로 잡았습니다. 개인 브랜치에서 9건 실패에 6분이던 테스트가 714건 통과에 55초가 되는 것까지 실측했지만 엔테나 dev에는 반영하지 못했습니다.
엔테나 프론트엔드는 4명이 나눠 쓰는 공용 영역이라, 내 몫은 내가 만든 API를 화면에 붙이는 연결 작업이 중심이었습니다. 화면 설계까지 끌고 가 보고 싶었지만 분업상 양보했습니다.
MoToK 미디어 서버에서 LiveKit 도입과 튜닝은 팀원 담당이라, 내가 만진 지점은 세션 종료 시 RemoveParticipant 한 곳뿐입니다. SFU를 직접 운영해 보는 경험은 다음으로 미뤘습니다.
기술적 한계와 개선 방안
MoToK은 STOMP simple broker와 인메모리 스케줄·레지스트리를 쓰는 한 스케일아웃이 불가능한 단일 인스턴스 전제입니다. 서버 재시작 시 진행 중 게임의 종료 스케줄도 유실됩니다(현재는 새 게임 시작 시 덮어써 복구하는 임시 대응). 다음 단계는 외부 브로커(RabbitMQ/Redis Pub-Sub)와 분산 락(ShedLock)으로 옮기는 것입니다.
SOOP은 이미 Redis를 쓰고 있으면서 로그인 제한만 ConcurrentHashMap으로 인메모리 레이트리밋을 남겨 뒀습니다. INCR + EXPIRE 카운터로 교체하면 그대로 수평 확장할 수 있습니다.
안심식탁은 테스트가 0건이고(최종보고서에 한계로 명시), SOOP은 컨트롤러 슬라이스(@WebMvcTest)가 비어 있습니다. 네 프로젝트 모두 커버리지 측정 도구(JaCoCo)를 붙이지 않아 수치로 말할 수 없습니다. 다음 프로젝트에서는 JaCoCo와 커버리지 게이트를 CI 1일차에 넣겠습니다.
엔테나는 배치와 API가 한 프로세스였습니다. @Scheduled 기본 스레드 풀은 1개인데 풀 크기를 따로 두지 않아 모든 배치가 한 스레드를 나눠 쓰고 있었습니다. 40분짜리 AI 판정 배치를 켜면 5초 주기 체인 인덱서가 멈추는 구조라, 켜기 전에 전용 데몬 스레드로 분리해 막았습니다. 돌아보면 애초에 배치 워커를 별도 프로세스로 분리하는 게 맞는 구조였습니다.
안심식탁은 3주라는 기간을 이유로 테스트를 건너뛰고(0건) 검증을 Swagger 수동 테스트에 의존했습니다. 최종보고서에 한계로 명시해 뒀지만, 기간이 짧을수록 오히려 회귀 비용이 크다는 걸 이후 프로젝트에서 체감했습니다.
안심식탁은 HTTPS를 끝내지 못했습니다. refresh 쿠키가 secure=false이고 CORS는 allowedHeaders=*여서, 팬텀 토큰으로 얻은 이득을 전송 구간에서 깎아먹는 구성이었습니다.

새로 배운 것
무상태를 포기하면 뭘 얻는가. 팬텀 토큰, RFC 9700 유예 창, Redis Lua 원자 실행, SETNX 멱등 가드, PostgreSQL append-only 트리거를 네 프로젝트에서 거의 매번 썼습니다. 그러면서 '동시에 들어오면 어떻게 되는가'를 먼저 묻는 게 습관이 됐습니다.
하루 1만 콜 한도, 쿼리당 45건, LLM 토큰 예산, 8명분 영상 추론 비용. 매번 이 제약을 먼저 재고 나서야 구조가 정해졌고, 이런 경험이 네 번 반복됐습니다.
시세 수집에 RestClient를 쓴 이유는 수집이 스케줄러 스레드에서 도는 블로킹 배치라 논블로킹으로 얻을 게 없고, 포털 페이징은 totalCount를 받아야 다음 장을 알 수 있어 어차피 순차이기 때문입니다. 그 뒤로 기술을 고를 때는 근거를 그 프로젝트 안에서 찾는 습관이 생겼습니다.
엔테나의 가입 500(ddl-auto가 못 푼 옛 NOT NULL)도 SOOP의 첫 조회 500(clearAutomatically)도 로컬에서는 멀쩡했습니다. 둘 다 '언제부터 달라졌나' 대신 '누가 이 경로를 타고 누가 안 타는가'를 갈라 보고서야 원인에 닿았습니다. 재현이 안 되면 조건을 좁히는 게 아니라 대상을 갈라야 한다는 걸 두 번 겪고 배웠습니다.

백엔드에서 프론트로 넘기는 인계 문서(회원가입), 명세 개정 초안, 미사용 코드 조사 문서를 남겨 다음 사람이 이어받을 수 있게 했습니다.
