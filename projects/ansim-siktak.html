안심식탁

알러지·기피 음식이 있는 사람이 외식할 때마다 겪는 "이 메뉴 먹어도 되나?"라는 불안을, 내 프로필 기준 메뉴 안전도(안전·주의·위험) 자동 판정으로 해소하는 외식 안전 플랫폼입니다. 2인 팀에서 팀장 겸 백엔드 전반을 맡아 인증·데이터·AI 연동을 설계·구현하고 ansim-siktak.site에 배포했습니다.

프로젝트 배경

사용 대상

알러지를 가진 사람, 특정 재료를 기피하는 사람, 그리고 가족·지인의 메뉴를 대신 골라야 하는 동반자입니다. 비회원은 식당 검색·조회가 가능하고, 회원은 알러지·기피 프로필 설정과 재료 등록·후기·챗봇·커뮤니티를, 관리자는 재료 마스터·공식 데이터·신고를 관리합니다.

문제의식

외식할 때 메뉴에 어떤 알러지 유발 재료가 들어가는지 알기 어렵습니다. 프랜차이즈는 공식 알러지표가 있지만 개인 식당·신규 메뉴는 정보가 거의 없어, 매번 직원에게 묻거나 위험을 감수해야 합니다. 핵심 문제는 "데이터 부재"였고, 정보가 없는 메뉴를 어떻게 다룰지가 서비스의 성패를 가른다고 보았습니다.

솔루션

데이터 출처를 3계층(공식 > 사용자 보강 > AI 추정)으로 물리 분리하고 출처별로 경고 강도를 차등 적용해 과장 없는 안전도를 판정합니다. 정보가 없는 신규 메뉴는 생성형 AI가 재료를 추정해 빈 DB(콜드스타트)를 메우되, 절대 "확정"으로 승격하지 않고 "불확실(AI 추측)"로만 분리 표기해 잘못된 안전 신호를 막았습니다.

기대 효과

사용자 후기·커뮤니티로 기여 데이터가 쌓이고 포인트·뱃지로 참여를 유도해, 시간이 지날수록 공식·사용자 데이터 비중이 늘며 판정 신뢰도가 높아집니다. 네이버/카카오 지도 링크 한 줄이면 식당이 자동 등록되어 데이터 축적의 진입 장벽도 낮췄습니다.

주요 구현

인증 / 보안

  • Phantom Token + Redis 인증 설계(JwtAuthenticationFilter) — 원본 JWT는 Redis에만 저장하고 클라이언트에는 SHA-256 해시만 전달합니다. 필터가 해시로 원본 JWT를 조회한 뒤 서명·만료·typ를 검증해 SecurityContext에 주입. JWT의 무상태성을 의도적으로 깨 서버 측에서 토큰을 즉시 철회할 수 있게 했습니다.
  • Access / Refresh 분리 + 로테이션 — Access 30분 · Refresh 14일로 분리하고, 재발급 시 이전 토큰을 무효화하는 Rotation 전략을 적용했습니다. 탈취·탈퇴·신고 처리 등 상황에서 세션을 즉시 끊을 수 있습니다.
  • 상태 비대칭 저장 — 인증 상태는 휘발성 Redis에, 도메인 데이터는 영속 RDS에 분리 보관해 "즉시 철회"와 "데이터 안전 영속"을 동시에 달성했습니다.
  • typ 교차 검증 — access / refresh 토큰의 용도를 typ 클레임으로 구분해 토큰 오용을 차단했습니다.

데이터 모델 / 안전도 판정

  • 데이터 출처 3계층 물리 분리 — 같은 "메뉴-알러지" 정보라도 출처를 테이블로 나눴습니다. official_menu_allergen(공식), menu_ingredient_log(사용자 보강 · is_uncertain), menu_ai_allergen(AI 추정 · likelihood_pct)로 분리해 신뢰 등급을 스키마가 직접 표현하도록 설계했습니다.
  • 신뢰도 기반 안전도 산정 — 출처와 신뢰도 임계값에 따라 안전 / 주의 / 위험 / AI추측 / 정보없음을 판정합니다. AI 추정은 절대 "위험(DANGER)"으로 승격하지 않고 "불확실"로만 표기해 과장 경고를 방지했습니다.
  • 이중 재료 마스터 — 자체 서비스용 ingredient(식약처 지정 22종 주요 알러지 플래그)와 프랜차이즈 공식용 allergen(표준 19종)을 분리해, 자유로운 재료 등록과 공식 데이터의 정합성을 동시에 확보했습니다.
  • 7개 도메인 · 33개 테이블 스키마 설계·구축 — user 허브를 중심으로 식당·메뉴·재료·후기·커뮤니티·관리 도메인을 모델링했습니다.

데이터 수집 / 콜드스타트 시딩

  • SeedRunner 백그라운드 시딩(ApplicationRunner) — 애플리케이션 기동 시 데몬 스레드로 전국 프랜차이즈 지점을 시딩합니다. brand_seed 플래그로 이미 시딩된 브랜드는 skip 하므로 매 기동이 멱등하고, 브랜드 단위로 실패를 격리해 다음 기동에 재시도합니다.
  • 쿼드트리 공간 분할로 카카오 한계 돌파 — 카카오 로컬 키워드 검색은 쿼리당 최대 45건(size 15 × page 3)만 회수됩니다. 대한민국 바운딩 박스를 결과가 45건 이하가 될 때까지 4분할 재귀(쿼드트리)해 전국을 완전 커버했습니다. 타일 경계 중복은 place id로 dedupe, 동명 오탐은 detectBrandId로 차단합니다.
  • 빈 DB(콜드스타트) 문제 해결 — 서비스 첫 기동부터 전국 지점 + 공식 메뉴·알러지 매핑이 채워져, 사용자 기여 데이터가 없는 초기에도 즉시 검색·안전도 판정이 가능합니다.

생성형 AI 백엔드 연동 (Spring AI)

  • 네이버 링크 메뉴 자동 추출(NaverLlmExtractor) — 네이버 지도 링크에 임베드된 Apollo state JSON을 ChatClient + BeanOutputConverter 구조화 출력으로 파싱해 이름·주소·좌표·메뉴를 추출하고 식당을 자동 등록합니다. 구조가 자주 바뀌는 네이버는 LLM으로, 카카오는 결정적 파싱(KakaoPlaceScraper)으로 처리하는 하이브리드 설계를 택했습니다.
  • AI 재료 추정(MenuAllergyEstimator) — 정보가 없는 신규 메뉴의 재료를 AI가 추정해 AI_ESTIMATED 출처로만 저장합니다(위험 승격 금지). 데이터 부재를 보완하되 안전 경계를 코드로 강제했습니다.
  • 알러지 안심 챗봇(AllergyChatService) — 의도 추출 → DB 그라운딩(메뉴·식당·사용자 프로필) → 답변 생성의 3단계 파이프라인으로, 환각을 줄인 컨텍스트 기반 응답을 제공합니다.

커뮤니티 / 운영

  • 후기 2트랙 — 메뉴 재료 등록(불확실 표시·메모)과 커스터마이징 후기(재료 제거 가능 여부·키오스크 옵션 등)를 분리해, 정보형 기여와 경험형 후기를 모두 담았습니다.
  • 게이미피케이션 — 포인트·뱃지·기여자 랭킹으로 사용자 데이터 기여를 유도합니다.
  • 관리자 단일 SPA(5탭) — 활동 로그·재료 마스터·신고 처리·회원 관리·공식 데이터 승격을 한 화면에서 운영할 수 있습니다.
  • 활동 로깅 — 사용자 활동을 로그로 적재해 기여도·통계 산출의 기반을 마련했습니다.

API 문서화

  • SpringDoc(Swagger) 전 컨트롤러 주석화 — 15개 컨트롤러 전부(15/15)에 OpenAPI 주석을 적용해, 프론트엔드·협업자가 API 계약을 한곳에서 확인할 수 있도록 했습니다.

Team & Role

팀 구성과 역할

2인 팀의 팀장 겸 백엔드 전반을 담당했습니다. 인증 아키텍처, 데이터 모델, 외부 데이터 수집, 생성형 AI 연동, 안전도 판정 로직까지 서버 영역을 직접 설계·구현했습니다.

  • 임대연 (팀장 · 백엔드) — Phantom Token + Redis 인증, 33테이블 DB 설계·출처 3계층 분리, 쿼드트리 전국 시딩, 생성형 AI 3종 연동(링크 추출·재료 추정·챗봇), 안전도 판정 로직, 활동 로깅.
  • 서현식 (팀원 · 프론트엔드 · 인프라) — Vue 3 SPA, 네이버 지도 기반 식당 탐색 UI, 인프라 및 배포.

깨달은 점

  1. 데이터가 없을 때 "모른다"를 설계하는 일이 핵심이었습니다.

    알러지 서비스에서 가장 위험한 건 잘못된 "안전" 표시입니다. 정보가 없는 메뉴를 AI로 채우되 절대 "확정"으로 승격하지 않고 "불확실"로 분리한 것, 출처를 테이블 단위로 물리 분리한 것은 "데이터의 출처와 확신 수준을 스키마가 직접 표현해야 한다"는 판단이었습니다. 기능이 아니라 데이터의 신뢰 등급을 설계하는 관점을 얻었습니다.

  2. 토큰의 무상태성을 일부러 포기한 이유가 있었습니다.

    표준 JWT는 한번 발급하면 만료 전까지 서버가 철회할 수 없습니다. 탈취·탈퇴·신고 처리처럼 즉시 무효화가 필요한 상황을 위해, 원본 JWT를 Redis에 두고 클라이언트엔 해시만 주는 Phantom Token으로 무상태성을 의도적으로 깼습니다. 인증 상태(휘발성)와 도메인 데이터(영속)를 저장소 차원에서 분리하니 "즉시 철회"와 "데이터 안전"을 동시에 달성할 수 있었습니다.

  3. 외부 데이터는 절대 깨끗하게 들어오지 않습니다.

    카카오는 쿼리당 45건 한계, 네이버는 거대하고 구조가 자주 바뀌는 Apollo state였습니다. 같은 "장소 수집"이라도 카카오는 결정적 파싱 + 쿼드트리 분할로, 네이버는 LLM 구조화 출력으로 처리하는 하이브리드가 필요했습니다. "한 가지 방법을 강요하기보다 소스 특성에 맞춰 수집 전략을 나누는" 실용적 판단을 체득했습니다.
