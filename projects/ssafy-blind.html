프로젝트 배경

사용 대상

SSAFY(삼성 청년 SW·AI 아카데미) 교육생 전반. Mattermost 계정을 보유한 현 교육생만 가입·로그인할 수 있습니다.

문제의식

교육 과정·취업·팀 갈등·평가에 대한 솔직한 고민을 털어놓을 공간이 없었습니다. 내부 공식 메신저인 Mattermost는 소속 반·이름이 모두 노출되고 사무국이 대화 내용을 열람할 수 있어 허심탄회한 글쓰기가 어렵고, 외부 커뮤니티는 SSAFY 교육생끼리만 통하는 맥락을 공유할 수 없습니다. "SSAFY 교육생인 건 확인하되, 누구인지는 알 수 없는" 소통 공간이 필요하다고 판단했습니다.

솔루션

Mattermost API를 인증 프록시로만 사용해 "현직 SSAFY 교육생 여부"만 확인한 뒤, 자체 JWT를 발급해 익명성을 완전히 보장하는 구조를 설계했습니다. 게시글·댓글의 author 관계는 DB에서만 유지하고 API 응답에서는 작성자 정보를 아예 제거해, 서버-클라이언트 사이 어디에서도 신원이 노출되지 않도록 했습니다. 신규 가입은 PENDING → ACTIVE 온보딩 플로우로 닉네임·기수·캠퍼스를 설정하되, 이 정보 역시 게시물과 연결되지 않습니다.

기대 효과

교육 과정의 고민·팁·후기 등 실명에서는 꺼내기 어려운 정보가 자유롭게 축적되어, 재학 중인 교육생뿐 아니라 이후 기수 교육생에게도 살아있는 내부 정보원 역할을 할 수 있습니다. 완전한 익명성이 보장되므로 솔직한 피드백과 건설적인 토론이 가능해집니다.

주요 구현

인증 / 보안

  • Mattermost 인증 프록시 구현(MattermostClient) — RestTemplate로 SSAFY Mattermost의 /api/v4/users/login을 호출해 교육생 여부만 확인한 뒤 자체 JWT를 발급. Mattermost 세션은 저장하지 않으므로 서비스에는 "인증됨" 이상의 정보가 남지 않습니다. 연결 타임아웃 3초 · 읽기 타임아웃 5초를 적용해 MM 서버 장애가 서비스 전체에 전파되지 않도록 했습니다.
  • Access + Refresh 토큰 분리 — Access Token(30분, stateless JWT)은 HttpOnly 쿠키로, Refresh Token(14일)은 SHA-256 해시 후 DB에 저장. 만료 시 단일 재발급 요청(single-flight retry)으로 토큰을 교체하고 이전 토큰을 즉시 무효화하는 Delete-on-rotate 전략을 적용했습니다.
  • JWT를 HttpOnly 쿠키로 관리 — CookieUtils 유틸리티로 JWT 쿠키 생성·삭제 로직을 일원화하고, httpOnly(true) + sameSite(Lax) 설정으로 XSS·CSRF 기본 방어를 적용했습니다.
  • JwtAuthFilter 설계 + shouldNotFilter() 크리티컬 수정 — OncePerRequestFilter를 상속해 쿠키에서 JWT를 추출·검증하는 필터를 구현. PENDING 상태 쿠키가 남아있을 때 /api/auth/login이 403으로 차단되는 버그를 shouldNotFilter()로 해결했습니다.
  • 로그인 레이트 리밋 — 동일 계정 5회 실패 시 300초 잠금, 600초 블록. 브루트포스 공격을 서비스 레이어에서 방어합니다.
  • PENDING → ACTIVE → DORMANT / WITHDRAWN 사용자 생명주기 — 신규 유저를 PENDING으로 생성한 뒤, 닉네임/기수/캠퍼스 설정을 마치면 User.completeOnboarding() 도메인 메서드로 상태를 전환하고 ACTIVE JWT를 재발급. @Setter 대신 도메인 메서드로 상태 변경을 캡슐화했습니다.

게시글 / 댓글 / 상호작용

  • 익명 게시글 CRUD — Post 엔티티에 author 연관관계는 유지하되, PostResponse.from()에서 작성자 정보를 의도적으로 제거해 API 응답 레벨에서 익명을 강제. 카테고리(FREE / JOB / QUESTION)와 검색·정렬을 지원합니다.
  • 조회수 벌크 UPDATE + 24시간 중복 방지 — @Query("UPDATE Post p SET p.viewCount = p.viewCount + 1 WHERE p.id = :id")로 DB 레벨 원자적 증가를 구현해 동시 요청 시 race condition을 방지. PostView 엔티티로 24시간 내 재조회를 중복 집계하지 않습니다.
  • N+1 해결 — 게시글 목록 조회 시 LEFT JOIN + COUNT JPQL 한 방 쿼리로 댓글 수까지 조회, 쿼리 수를 O(N) → O(1)로 감소(게시글 20건 기준 21 → 1).
  • 중첩 댓글(1-depth) + OP/익명N 별칭 — parentId로 대댓글 구조를 지원하고, 스레드 내에서 원작성자(OP)와 다른 참여자(익명1, 익명2…)를 구분하는 별칭 시스템을 적용해 익명성을 유지하면서도 대화 맥락을 파악할 수 있습니다.
  • 4종 리액션 — LIKE / HELPFUL / INFORMATIVE / EMPATHY 중 게시글당 1종 선택. PostLike(post, user) 유니크 제약으로 중복을 DB 레벨에서 차단합니다.
  • 익명 투표(Poll) — 게시글당 2~8개 선택지 생성, 1인 1표 제한, 집계 결과만 반환해 투표 주체를 알 수 없도록 설계했습니다.
  • Q&A 답변 채택 — QUESTION 카테고리 게시글에서 답변을 채택하면 게시글에 "Solved" 배지를 표시하고 채택된 댓글을 상단 고정합니다.
  • 북마크 · 신고 · 알림 — 북마크 저장, 누적 신고(≥5회 자동 숨김), 댓글·리액션 알림(읽음 처리 포함)을 구현했습니다.
  • Cascade 댓글 삭제 — @OneToMany(cascade = ALL, orphanRemoval = true)로 게시글 삭제 시 연관 댓글을 자동 삭제, FK 위반 방지.

어드민 / 운영 기능

  • 어드민 대시보드 — 신고 통계(요약·사유별·14일 일별 추이) 조회, 신고 게시글 숨김/복구, 공지 핀 고정 기능을 제공합니다.

  • 기수/캠퍼스 라운지 필터 — 같은 기수, 같은 캠퍼스 글만 보는 필터를 카테고리·검색과 직교 조합할 수 있어 원하는 맥락의 글을 빠르게 탐색할 수 있습니다.
  • Flyway 스키마 버전 관리 — V1 기준선부터 V6까지 6단계 마이그레이션으로 프로덕션 스키마 변경 이력을 관리합니다.

프론트엔드

AI 페어 프로그래밍 도구(Claude)를 적극 활용해 골격을 빠르게 잡고, 인증 가드·페이지 흐름·UX 디테일을 직접 검토·조정했습니다.

  • AuthContext + PrivateRoute 인증 가드 — 앱 마운트 시 GET /api/auth/me로 쿠키 유효성을 확인하고, 미인증 시 로그인 페이지로 리다이렉트. useAuth() 커스텀 훅으로 어디서든 인증 상태에 접근 가능.
  • Axios 단일 재발급 인터셉터 — 401 응답 시 Refresh Token으로 한 번만 재발급을 시도하고, 동시에 발생한 요청을 큐에 적재해 토큰 갱신 완료 후 일괄 재전송합니다.
  • 마크다운 렌더링 — react-markdown + remark-gfm + rehype-highlight로 게시글·댓글에서 코드 블록 구문 강조를 지원합니다.
  • 페이지 구성 — Login → Onboarding → Feed(필터/정렬) → PostDetail → PostCreate/Edit → Settings → Feedback → Admin 대시보드로 사용자 여정 전체를 구현했습니다.

문제 해결

로그인 직전 PENDING 쿠키 때문에 로그인 API가 403으로 막히던 인증 필터 버그를 해결했습니다.

문제

온보딩을 마치지 않은 PENDING 사용자의 JWT 쿠키가 남아 있으면, 다시 로그인하려 해도 /api/auth/login 요청이 403 Forbidden으로 차단됐습니다.

원인

OncePerRequestFilter 기반 JwtAuthFilter가 모든 요청의 쿠키를 검증하다 보니, "로그인하러 가는 길"까지 유효한 인증을 요구하는 모순이 생겼습니다.

시도

필터의 shouldNotFilter()를 오버라이드해 /api/auth/** 인증 경로는 JWT 검증을 건너뛰도록 필터의 책임 경계를 분리했습니다.

결과

PENDING 쿠키가 남아 있어도 로그인·토큰 재발급이 정상 동작했고, 인증 필터의 "검증 대상"과 "통과 대상"을 명시적으로 가르는 설계 기준을 세웠습니다.

깨달은 점

  1. "익명을 보장한다"는 요구사항은 아키텍처 전체의 문제였습니다.

    단순히 화면에서 이름을 숨기는 것과 API 응답 자체에서 작성자 정보를 제거하는 것은 보안 수준이 완전히 다릅니다. Post.author를 DB에는 남기되 PostResponse.from()에서 매핑하지 않는 방식을 택한 것은 "DB 관리 편의"와 "API 레벨 익명성"을 모두 만족시키기 위한 설계 판단이었습니다. 이 과정에서 "어느 레이어까지 정보가 흘러야 하는가"를 기능 단위가 아닌 아키텍처 단위로 사고하는 습관이 생겼습니다.

  2. 토큰 보안은 "발급"이 아니라 "폐기"에서 결정됩니다.

    Access/Refresh 토큰 분리 후 진짜 문제는 "언제 무효화하느냐"였습니다. Refresh Token을 평문으로 저장하면 DB 유출 시 대규모 세션 탈취로 이어집니다. SHA-256 해시 저장 + Delete-on-rotate(재발급 시 이전 토큰 즉시 삭제) 전략을 선택한 이유는 탈취된 토큰의 유효 창을 최소화하기 위해서였고, 이 설계 결정이 결국 "보안은 흐름 전체를 끊는 곳에서 달성된다"는 교훈으로 남았습니다.

  3. 테스트는 "코드가 돌아가는지"가 아니라 "DB 계약이 유지되는지"를 검증해야 했습니다.

    서비스 레이어 단위 테스트만으로는 Cascade 삭제·유니크 제약·JPQL 집계가 실제 스키마와 맞는지 알 수 없었습니다. @DataJpaTest(H2 MySQL 모드)로 리포지터리 레이어를 별도 검증한 덕분에, 게시글 삭제 시 투표·리액션이 누락 없이 제거되는지, LEFT JOIN COUNT가 NULL을 0으로 처리하는지를 배포 전에 잡을 수 있었습니다. "통합 테스트는 인터페이스가 아닌 계약을 검증한다"는 관점을 실제 버그를 통해 체득했습니다.
